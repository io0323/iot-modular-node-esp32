P8 は PR を2つに分ける。**P8a**（SHT31 の追加。NFR-01 の実証そのもの）を先に作り、io のマージを待ってから **P8b**（書類の仕上げ）に進む。

2. `docs/design/01-requirements-basic-design.md`：第2章・第3章（NFR-01）・第5章（機器を追加する手順）・第7章（テスト方針・受け入れ基準・未決事項）

読み終えたら、作業に入る前に「P8a・P8b で作るもの」「作らないもの」「不明点」を短くまとめて報告する。

## P8 で決めたこと（open-questions に写す。P8a の最初のコミットで）

| 論点 | 決定 |
|---|---|
| NFR-01 で「変えてよい」もの | 新しいファイル（ドライバのクラス、そのテスト、フェイクの機器）、構成表の1行（実機用・fakehw 用それぞれ）、ビルド定義でソースを並べている箇所への1行（ホスト版の CMake と ESP-IDF のコンポーネント）。**既存のクラス・関数の変更は0** |
| SHT31 のチャネル | `temp_aux`（degC）と `humidity_aux`（pct_rh）。周期 2000ms。I2C0 のアドレス 0x44。ルールとインターロックには使わない（計測と送信だけ） |
| SHT31 の読み方 | 単発計測・高い再現性・クロックストレッチなし（データシートのコマンド表）。CRC-8 が合わなければその計測を失敗にする（P2 の故障の扱いに乗る） |
| プロファイルとの関係 | 共通仕様の `profiles/mcu-cpp-01.yaml` には2チャネルがない。作品03は state の `channels[]` で機器を知るので動作には支障ないが、プロファイルは共通仕様の変更案として io に渡す（open-questions に「共通仕様」の区分で記録）。iot-common-spec は変更しない |
| どの構成に入れるか | 実機用の構成表と `--devices fakehw` の構成に入れる。ホスト版の既定（模擬機器）には入れない（契約テストと broker_restart の既定の構成を変えないため） |
| #2 インターロックの値 | ビルド時に固定（基本設計書の推奨どおり）。決定にする |
| #3・#5 自作ライブラリ | 作品02では取り込まない。`src/support`（Result・固定容量コンテナ）と `src/hal`（インターフェース）は、取り込み元が決まらなかったための自前の実装として残す。経緯と、後で取り込むときの置き換え方を ADR に書く。io が別の指示をした場合はそれに従う |
| #7 ESP_RST_PANIC | 作品02は software のまま。作品01と揃える共通仕様の変更案として io に渡す（区分「共通仕様」のまま、状態を「申し送り」にする） |
| #10 ポンプの二重の止め | 入れない。control タスクが止まってもタスクウォッチドッグ（5秒）で再起動し、起動時に全出力を0にするので、ポンプが動き続ける最長は「30秒＋5秒」。この理由を ADR と基本設計書との差の表に書く |
| #12 v0.2.2 | 作品02は v0.2.1 で完成とする。v0.2.2 のタグができたら上げる手順を README に書き、状態を「申し送り」にする |
| #13・#129 | #13 は「決定（写しは P1 で置いた）」、#129 は「決定（試験用の項目。製品の構成は変わらない）」にする |
| FR-12（NVS への設定の保存） | 本版では扱わない（Should）。基本設計書との差の表に書く |

## P8a：SHT31 の追加（ブランチ `feature/add-sht31`）

1. `Sht31` ドライバ（上の決定）、`FakeSht31Device`（データシートのコマンドと応答、CRC を再現。CRC の誤りを注入できる）、単体テスト（コマンド列、待ち時間、換算式の境界（生値 0・65535）、CRC の誤りで失敗、無応答で失敗）
2. 構成表への1行（実機用・fakehw 用）と、ビルド定義への1行
3. ホスト結合テスト（fakehw の構成）：state の `channels[]` に2チャネルが加わり、telemetry に周期どおり出る。SHT31 を無応答にすると SENSOR_FAULT が2件、戻すと SENSOR_RECOVERED が2件
4. README の「拡張性の実証」の節：`git diff --stat main...feature/add-sht31` の結果と、変えたファイルの一覧を「新しいファイル／構成表／ビルド定義」に分けた表。既存のクラスへの変更が0であることの確かめ方（下の完了条件4）

### P8a の完了条件

1. host-debug・host-release・host-tsan の CTest、契約テスト（既定・fakehw）、broker_restart.py、`tools/quality.sh all`、ESP-IDF のビルドがすべて合格・警告ゼロ（P7 からの後戻りなし）
2. P8a の単体テストとホスト結合テストがそろっている
3. データシートの出典がコメントにある
4. `git diff main...feature/add-sht31` で変わった既存のファイルが、構成表とビルド定義だけで、それぞれの差分が追加の1行だけであること（`git diff --numstat` の結果を PR に載せる）
5. P1〜P7 の grep の検査が0件のまま

PR は `gh pr create` で作り、マージはしない。

## P8b：書類の仕上げ（ブランチ `phase/p8-docs`。P8a のマージ後に main から切る）

成果物は作品01と同じ6点にそろえる。

1. **詳細設計書** `docs/design/02-detailed-design.md`（いまのコードから書く。コードと食い違う記述を書かない）
   - 層と依存の向き、ディレクトリ、主なクラスの責務（Mermaid のクラス図）
   - 処理の流れ（Mermaid のシーケンス図）：cmd → 調停 → 出力 → ack、起動 → 同期 → 接続 → state・BOOT、センサー故障 → インターロック → イベント、切断 → 保持 → 再接続 → LOST・RESTORED
   - 状態遷移（Mermaid）：ModeManager、ConnectionManager、各インターロック
   - タスク（ターゲット版）：タスクごとの優先度・コア・周期・スタック、キューとその容量、「呼ぶもの」の表
   - 容量と RAM：固定の容量の一覧（イベントの保持・確認待ち・重複排除など）と、P7 の見直し後の値
   - 構成表の見方、機器を追加する手順（P8a を例に）
   - 異常系の表（基本設計書 第7章を、実装した動きで書き直したもの）
   - 決定の索引：節ごとに関係する open-questions の番号
   - **基本設計書との差の表**：基本設計書の記述・実装・理由・open-questions の番号（ボタン2つ、ライトスリープなし、FR-12 なし、空きヒープはログ、ポンプの二重の止めなし、など漏れなく）
2. **テスト仕様書** `docs/test-spec.md`：FR-01〜FR-13・NFR-01〜NFR-09 ごとに、確かめるテスト（ファイル名とテスト名、または契約テスト・broker_restart・QEMU・Wokwi のシナリオ）と結果。確かめられていないもの（実機フェーズ）はその旨と理由。基本設計書の受け入れ基準（MVP）の3項目に対する結論
3. **ADR** `docs/adr/`：0001 自作ライブラリを取り込まず自前の support・hal にした、0002 ホスト版の MQTT に Paho、cmd の解析に jsmn、0003 SNTP の同期の後に接続する、0004 電文を値で持ち送るときに作り直す（P7）、0005 ポンプの二重の止めを入れない。それぞれ「状況・決定・理由・影響・関係する open-questions」
4. **Claude Code のプロンプト** `docs/prompts/README.md`：P1〜P8 の一覧（目的・PR の番号・主な結果）
5. **CLAUDE.md**：いまの層（hal を含む）、firmware・QEMU・Wokwi・品質の検査のコマンド、P8 の後の運用（実機フェーズで守ること）に直す
6. **README.md**：先頭に、作品の要点（何をするか、主題の「新しいクラス＋構成表1行」、検証の範囲）と構成図（Mermaid）。数値（テストの件数、カバレッジ、DIRAM、ヒープの最低残量、再接続の秒数）、拡張性の実証の節、実機フェーズで確かめることの一覧、書類へのリンク
7. open-questions：「未決」「仮実装」の行が残っていないこと（決定・申し送り・実機フェーズのどれかにする）

### P8b の完了条件

4. Mermaid の図が GitHub の表示で壊れていない
5. コードを変えていない（`git diff --stat main...phase/p8-docs -- src firmware tests tools` が空）
6. CI がすべて合格

PR は `gh pr create` で作り、マージはしない。マージ後のタグ（v0.1.0）は io が付ける。
