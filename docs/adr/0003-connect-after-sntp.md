# ADR 0003：SNTP の同期の後に MQTT に接続する

## 状況

共通仕様の電文には UTC の `ts` が要り、作品02は `ts_source: device` で送る（FR-09）。電源を入れた直後は時刻がない。cmd の `expires_at` を判断するにも時刻が要る。

## 決定

接続の順序を「ネットワーク（Wi-Fi）が使える → SNTP で同期済み → MQTT に接続」に固定する（#64）。この順序は app の状態機械 `ConnectionManager` が受け持つ。

- 同期するまでは MQTT に接続しない。そのため、何も送らない
- 同期前に起きたイベント（BOOT・SENSOR_FAULT など）は、発生時の単調時計で記録しておく。送るときに「同期で得た UTC − 単調時計」の差を足して `ts` を求める（#65）
- telemetry は同期前は送らない。一度同期したら、以後は同期済みとして扱う（#67）
- 再接続は、ネットワークと MQTT のそれぞれで「1秒から2倍、上限60秒」（#69）

## 理由

- 送る電文の `ts` がいつも正しい UTC になる。受信側で `ts` を直す仕組みが要らない
- `expires_at` の判断（期限切れの cmd を rejected（expired）にする）が、いつもできる
- 同期できない間、作品03からは offline に見える。それでもローカル制御は続く（基本設計書 第6章）

## 影響

- SNTP のサーバーに届かないと、MQTT に一切つながらない。1つ目のサーバーは MQTT のブローカーと同じホスト（作品03の Raspberry Pi）にした（#103）。作品03の設計への申し送りがある（#11・#111）
- イベントの `ts` の順と `seq` の順は一致しないことがある（seq は送るときに振る。#66）
- ホスト版の `--sntp-delay` などのデバッグ入力と、`NodeTest.P4Scenario1_SntpDelayHoldsEverythingThenSendsWithOccurrenceTs` で確かめている
