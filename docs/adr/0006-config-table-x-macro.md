# ADR 0006：構成表を X マクロの「1行が1台」の表にした（P8）

## 状況

作品の主題（NFR-01）は「新しい機器の追加で変更するのは、新しいクラスのファイルと構成テーブル1行だけ。既存クラスは変更しない」である。ところが P3〜P7 の実機用の構成表は、1行が1台の表になっていなかった。`config::HwRig` と fakehw 用の `config::FakeHwRig` はクラスで、機器ごとに次を書いていた。

- メンバー変数
- コンストラクタの初期化子
- `std::array<domain::ISensor*, 3> sensors_` の一覧

P8 で SHT31 を足そうとして、このことが分かった（#145）。リファクタリングの前の構成表（a09ad65）に SHT31 を実際に足して数えると、次の変更が要った。

- 変える既存のファイル：hw.hpp・hw.cpp・fakehw.hpp・fakehw.cpp の4つ
- 差分：追加16行・変更3行。変更は `sensors_` の大きさ、`sensors_` の並び、FakeHwRig の初期化子
- 変わる既存のクラス：HwRig と FakeHwRig の2つ

## 決定

構成表を、X マクロの「1行が1台」の表にした（PR #8。振る舞いは変えない）。

- 表のファイル
  - `src/config/hw_table.hpp`：`NODE_SENSOR(型, 名前, (前半の引数), 周期, (チャネル...))` と `NODE_ACTUATOR(型, 名前, (前半の引数), (仕様), インターロック)`
  - `src/config/fakehw_table.hpp`：`NODE_FAKE_I2C(型, 名前, アドレス)` と `NODE_FAKE_I2C_ARGS(型, 名前, (引数), アドレス)`
- クラスへの展開：HwRig・FakeHwRig は、表を何回か読み、次を展開する
  - メンバー
  - チャネルと仕様の静的な値（ドライバが参照で持つため）
  - 初期化子
  - 一覧とその大きさ
  - アクセサー
  - バスへの登録
- 機器を足すときに変えるもの：表に1行と、ドライバ（またはフェイク）のヘッダの include を1行

その後の P8a（PR #9）では、SHT31 を足すための既存のファイルの変更が「追加1行×7」になった。内訳は、構成表4つ（表の行2つと include 2つ）と、ビルド定義3つ。

## 理由

- 機器の追加を、表の1行（と include の1行）にするため。HwRig と FakeHwRig のメンバー・初期化・一覧の大きさが、表から決まる。足し忘れも食い違いも起きない
- X マクロは、C と C++ で表を扱うときの広く知られた書き方で、コンパイラの機能に頼らない。C++20 の機能は使っていない
  - `__VA_OPT__` は使っていない。cppcheck 2.13 が読めないため、引数のないフェイクと引数のあるフェイクで、マクロを分けた
- 静的に確保する形（ヒープを使わない。NFR-03）と、ドライバが参照で持つチャネルと仕様を静的な値に置く形が、そのまま保てる

## 代わりに失ったもの

- **読みにくさ**：表の行は長く、引数を括弧でくくる決まり（`(前半の引数)`・`(チャネル...)`）を知らないと読めない。展開の結果は、ソースを読んでも直接は見えない。表のファイルの先頭に書き方を書き、マクロは `src/config` の中だけで使う
- **clang-tidy の抑止**：`cppcoreguidelines-macro-usage` は関数のようなマクロを指摘する。`.clang-tidy` の `AllowedRegexp` で、表のマクロの名前（`NODE_SENSOR`・`NODE_ACTUATOR`・`NODE_FAKE_I2C`・`NODE_FAKE_I2C_ARGS`・`NODE_CONFIG_UNPAREN`）だけを許した（docs/quality.md の抑止の一覧）
- **Doxygen**：表をクラスの中で読むため、`INCLUDE_PATH = src` が要る。展開されたメンバーとアクセサーは、Doxygen の文書に出ない

## ほかの案を選ばなかった理由

- **テンプレートの型の並び**：`std::tuple<Bme280, Bh1750, ...>` のように、機器の型を並べる案。型の並びと、各機器のコンストラクタの引数を、別々に書くことになる。引数（hal の参照・アドレス・チャネル）は実行時の値なので、型の並びだけでは表にならない
  - 行ごとに「型と引数を持つ記述子」を並べ、`std::apply` でメンバーを作る形も考えた。この形では次の点が問題になる
    - 動かせない（コピーもムーブもできない）ドライバを、tuple の中にその場で作る必要がある
    - チャネルの表を、静的な領域に置く必要がある
  - 書き方がマクロより難しくなり、エラーのメッセージも読みにくい
- **プレースメント new と固定のバッファ**：表を .cpp に閉じ込め、hal の参照を受けてから機器をバッファの中に作る案。`new` の検査（P1 の grep）に引っかかるうえ、寿命と型の管理を自分で書くことになる
- **今のまま（クラスに書き足す）**：NFR-01 を満たさない

## 影響

- 機器を足す手順（基本設計書 第5章）は、「`config/devices.cpp` に1行」ではなく次の2つになった。詳細設計書の「構成表の見方と機器を追加する手順」に書いた
  - `config/hw_table.hpp`（と `fakehw_table.hpp`）に1行
  - そのヘッダの include を1行
- 模擬機器の構成表（`config/devices.cpp` の `SimRig`。ホスト版の既定の構成）は、表にしていない。リファクタリングの前の HwRig と同じく、機器ごとのメンバーと一覧を書く形のままである。SHT31 はこの構成に入れていない（#143）。模擬機器を足すときは、SimRig のメンバー・一覧・大きさの数行を変えることになる
